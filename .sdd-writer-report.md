## What does NOT round-trip yet

Nothing observed in the fixture corpus. Everything the reader supports
(per `model.py`'s `__all__` and the fixture's coverage) round-trips
exactly, including GUIDs, list/element order, non-ASCII (Greek) text,
`Decimal`/`date`/`datetime` variable values, and overlapping selections.

Two edge cases worth flagging to the consuming app, not because the writer
fails them, but because they are inherent, pre-existing limits of the
**reader's** XML-text handling (the writer cannot fix these without
changing reader behaviour, which was out of scope):

1. **`description=""` (empty string) is indistinguishable from omitted on
   round trip.** `to_qde` writes `<Description></Description>` for an
   empty string, but lxml reports `.text` as `None` for an element with no
   text node, so `parse_qde` reads it back as `None`, not `""`. This is a
   property of the reader (`_child_text()`), not something the writer
   introduces — but any code exporting a `Project` should not rely on
   `""` surviving through this library for `Description`/`PlainTextContent`
   fields. `None` vs. non-empty string both round-trip correctly.
2. **Nothing else in the modelled construct set is lossy.** Everything
   that has a defined field in `refi_qda.model` (six selection types, five
   source types, transcripts/syncpoints, cases/variables incl. all six
   `VariableValueScalar` types, sets, links, graphs, notes) round-trips.

## `source_files` semantics (relevant to the consuming app's export path)

`write_qdpx(project, path, *, source_files=None)` does **not** decide or
rewrite which sources are internal vs. external. That's already recorded
in the `Project` itself via each source's `path`/`plainTextPath`
attribute (e.g. `internal://<guid>.txt` vs. `relative://...`/`absolute://...`),
exactly as `refi_qda.container.parse_source_path`/`SourceScheme` already
distinguish them for the reader. `source_files` only supplies the on-disk
bytes for whichever of those already-`internal://` sources you want
physically embedded in `sources/`; the app must set the source's
`path`/`plain_text_path` to `internal://<filename>` itself before calling
`write_qdpx`. Passing a GUID whose source is `relative://`/`absolute://`,
or has no path at all, raises `ExternalSourceError` rather than silently
reinterpreting it as internal.

## Design notes / concerns

- **XSD source of truth**: this environment's scratchpad did not have the
  `refi.pdf`/`refi.txt` files referenced in the task (they were not
  present in the session's scratchpad directory). I re-fetched the
  official REFI-QDA v1.5 PDF from
  `https://openqda.github.io/refi-tools/docs/standard/REFI-QDA-1-5.pdf`
  (found via web search) and extracted the embedded `Project.xsd` (section
  5.3) directly from the PDF text via `pypdf`, then used that as the
  authoritative element-order/attribute-casing source — not guesswork.
  One concrete finding from doing this properly: the hand-authored
  fixture's `PDFSource` has `<Representation>` *before* `<PDFSelection>`
  in the XML, but the real XSD's `PDFSourceType` sequence is
  `Description?, PDFSelection*, Representation?, Coding*, ...` (selections
  before the representation). The writer follows the XSD order, not the
  fixture's order — this is harmless for this library's own round trip
  (the parser is order-agnostic, using `.find()`/`.findall()`), but would
  matter for actual XSD validation, which nothing in this repo currently
  runs (no vendored schema).
- **No XSD validation was run** against the writer's output, by design —
  this repo does not vendor the schema (licence reasons, see
  `schema/README.md`), and I did not have a local `schema/Project.xsd` to
  point `refi_qda.validator.validate()` at. Order/casing was produced by
  reading the XSD text directly rather than validated by machine; worth an
  explicit XSD-validation pass once a schema copy is available locally.
- **`Decimal`/float round trip** relies on `Decimal.__str__` reproducing
  the same digit string the parser constructed (`Decimal("3.140")` stays
  `"3.140"` through a round trip); this is correct per Python's `decimal`
  semantics but is a detail worth knowing if the consuming app ever
  constructs `Decimal` values via `float` first (which loses precision
  before this library ever sees it — not this library's problem, but a
  common footgun for callers).
- Added a new test-only helper, `tests/roundtrip_diff.py`
  (`first_divergence(a, b)`), used instead of `conformance/diffing.py`'s
  `diff_projects()` — that module intentionally matches objects by name
  (built for comparing against independent vendor re-exports that don't
  preserve GUIDs), which is the wrong tool for verifying this library's
  own exact, GUID-preserving round trip. `first_divergence` walks both
  trees positionally and reports the first differing field path.
